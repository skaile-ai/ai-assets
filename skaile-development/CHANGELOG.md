## [Unreleased]

### Changed
- `doc` and `faq`: the `prerequisites.reads` / `produces` entries are objects (`- path: "..."`), not plain strings. `skaile validate` in `@skaile/workspaces` 10.16.0 rejects the string form, which made `skaile update` refuse the whole `skaile-development` preset in a consumer (skaile-ai/platform#12106).
- `ship` is renamed to `deliver` (2.0.0) and cut from 1,492 to about 450 lines plus two reference files (#308). Claude Code 2.1.330 and later reserves `/ship` and `/steward` and does not load a custom skill with those names. **Consumers:** re-deploy; the skill directory is now `.claude/skills/deliver/`, and a brief or script that names `ship` or its path must change. What changed in the flow: the size of the work decides the route (`small` = inline, no plan file, no subagents); the `issue` input also accepts a pull request and resume reads the issue's linked PRs; one push before the PR opens; the unattended rules are part of the skill (hand back before the merge, poll with `--timeout 480`, at most two fix pushes, hand back when only a check that waits for a person is pending); the watch detail moved to `references/watch.md`; the platform docs-impact step moved to `references/platform.md`. Removed: the inputs `category`, `branch_slug` and `complexity`, the `EMIT` lines, the `implement` / `review` agent types (they do not exist; `general-purpose` is used), the post-merge mirror copy, the `commit-spec.md` read. `references/platform.md`: the deploy path now goes through `deploy-candidate`, `scripts/pre-merge-fresh-check.sh` runs before every merge, the invariant suites use `bun run test:invariants`. The main checkout of a submodule clone is found through `core.worktree` (#268). Preset `@skaile-ai/skaile-development` 1.2.0 lists `deliver`; agent `skaile-development` 1.4.2 routes to it; `meat` 1.0.1 and `issue-bar` 1.0.1 name it.
- Reuse check before building: agent `skaile-development` 1.4.1 (`SOUL.md` step 2) and `ship` 1.11.1 (STEP 6, required for features and for chores that add a package, service or integration) run the org-internal `skaile-inventory` skill where it is installed and record a reuse / extend / port / build verdict per candidate. `skaile-stack-decide` routes "what's on the shelf?" to it and marks its own ecosystem inventory as history. The skill itself is not part of this repo or the preset. `DOMAIN.md` now lists every skill in the domain: `skaile-stack-decide`, `postxl`, `component-builder`, `good-morning` and `migrate-skaile-manifest` were missing, and `meat` and `issue-bar` were missing from the Skills table. The versions skip 1.4.0 and 1.11.0 because those numbers are already published in the store and cannot be reused.

Platform retired `_devlog/entries/`, which `devlog` writes to. The `devlog` skill itself stays in the domain for repos that still keep a dev log.

Agent `skaile-development` 1.2.1: the `SOUL.md` routing row for a new skill or domain points at the skaile CLI's bundled `skaile-manage-workspace` skill instead of `ai-resource-navigator`. `migrate-skaile-manifest` and the `skaile-stack-decide` references no longer name `skill-builder` / `domain-builder`; they point at the CLI's bundled `authoring-skaile-assets` skill.

Consumers: replace `bundle:skaile-development@skaile-ai#^2.0` with `preset:@skaile-ai/skaile-development#^1.0` in `dependencies:`. It pointed at `../../../../ai-asset-management/agents/skaile/agent.yaml`, one level above the repo root, so it never resolved; and even a correct path would only have affected `skaile install` (`asset-manager` `applyExtendsMerge`), because the runner's composition resolver ignores `extends`, so install and runner would have built two different agents. The `# Family alias:` comment on `model` matches the `skaile-forge` agents.

### Fixes
- `ship` 1.10.1: STEP 10b no longer says the `docs_impact=none` reason goes in the PR body (that section is gone). The reason goes in the `docs_impact=none reason=<…>` record; a `none` change carries no triggering `whats-new*` marker, so it needs no changeset marker.
- `git` `deploy` (retired) now says never to push `deploy`: the platform `deploy` branch is protected by the `deploy-protection` ruleset, and a release deploys when the Version PR merges in the 06:00-07:00 Berlin window (#192). `ship` 1.9.1 `references/platform.md` says the same.
- `git` `finish` merge: a BLOCKED PR is classified from `gh pr checks --required --json name,bucket` (read the JSON, not the exit status), so a red required check stops instead of arming auto-merge. Auto-merge is armed only for a pending required check or a required review; a block nothing will clear (no required checks, or all pass or skipping) stops and names the gate. An UNKNOWN merge state, usual right after the PR is created, gets one re-probe after about 3 s before it stops. Every `git-state.json` write is anchored at `<repo_root>`, and branch mode resolves `repo_root` itself. `DOMAIN.md` and `worktree_patterns.md` say changes land by PR instead of claiming every default branch is protected.
- Every repo is standalone; the archived `skaile-dev` shell is no longer treated as live (#189). `DOMAIN.md` states the rule and no longer marks `references/test_stack_map.md` authoritative (the target repo's `CLAUDE.md` wins). `test_stack_map.md` gives per-repo commands for workspaces, platform, ai-assets, store and brand. `ship` 1.9.0 resolves the target repo as the main checkout of a standalone clone (never a linked worktree), stops reading the shell `CLAUDE.md`, and puts worktrees beside the clone at `<repos_root>/.worktrees/<repo>-<number>`. `git` uses per-repo format commands, a worktree beside the clone, an unpushed-commit guard instead of submodule pushes, its `finish` merge squash-merges on GitHub only (`gh pr merge --squash`, no local squash, never `--admin`, no `--delete-branch`), is safe to re-run (an already merged PR or a recorded `auto_merge` status skips to cleanup), lets `mergeStateStatus` pick the path (merge now when CLEAN, UNSTABLE or HAS_HOOKS; when BLOCKED, stop on a red required check or requested changes and arm auto-merge only for pending required checks or a required review, then never offer `discard`; stop on DIRTY, BEHIND, DRAFT or UNKNOWN), keeps its state at `<repo_root>/_implementation/git-state.json`, and cleans up in a safe order (worktree, default branch, `pull --ff-only`, then the branch), and its `sync` and `deploy` modes now stop with a pointer (the platform deploys when its Version PR merges). `commit-spec.md` drops package-path scopes and states that no `---agent---` block is used. `test`, `implement`, `proposal`, `e2e-platform` 1.3.2, `ready`, `postxl` 1.0.2, `jenkins-debug`, `devlog`, `doc_tiers.md` and `readiness_criteria.md` run commands and write docs in the target repo.
- `ship` 1.7.2: STEP 15 puts `Closes #<issue_number>` in the squash-merge body and then reads the issue state, closing the issue by hand with a comment if the merge left it open. Before, the skill left the keyword out of the squash body, and merged issues stayed open.
- `ship` 1.7.1: STEP 10b treats a `whats-new-fix:`-only changeset as `docs_impact=none`, matching the platform CI guard, instead of demanding a capabilities-doc edit and an ai-assets PR.

### Enhancements
- `ship` 1.10.0: the `platform-guide` skill moved to `skaile-ai/platform` (`features/platform-guide/`). STEP 10b edits it in the platform worktree and runs `bun run guide:embed`, so the guide merges and deploys with the change; there is no ai-assets guide PR, no clone of ai-assets and no guide merge in Phase 13b. A declined doc is a `<!-- guide: n/a — … -->` / `<!-- capabilities-doc: n/a — … -->` marker in the changeset, checked by Build & Test, instead of the `## Docs` PR-body section.
- `ship` 1.7.0: the platform capability-docs sync moved from post-merge Phase 13b (conditional, "only if accessible") to Phase 8b, before the commit. The capabilities doc now rides in the same PR, the `platform-guide` skill gets its own ai-assets PR (cloned when no checkout exists) merged with the platform PR, and the PR body carries a `## Docs` section that platform CI parses. Headless or forked runs stop before the merge gate and never reached the old step, which is why the docs were never updated.
