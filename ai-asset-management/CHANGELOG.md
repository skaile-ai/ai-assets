# Changelog — ai-asset-management

## [Unreleased]

### Changed
- Agent `skaile`: its own `RULES.md` is deleted. It was line-for-line the `skaile-safety` ruleset the agent already composes (one `<>` vs `↔` apart), so the prompt carried every rule twice (`## Constraints` and the composed block). The composed `_agent-parts/rules/skaile-safety/RULESET.md` is now the single copy. The ruleset's "validate with `npx gitagent validate`" rule now says `skaile validate` (the upstream CLI only knows spec 0.1, and `agent.yaml` is 0.2 here); `docs/agents.md` says the same. `skaile-development` no longer composes this ruleset (see its CHANGELOG): it is concept-pipeline rules.
- `catalogs/dist/*.catalog.json` is build output compiled from `catalogs/*.catalog.yaml` by `catalogs/build.ts`, whose compiler lives in the consumer monorepo (`agent-framework/asset-manager`), so it cannot be regenerated from this repo and lags the YAML (compiled 2026-04-12: it lists fewer entries than the manifests now name). `scripts/presets-resolve.test.sh` section 6 checks that every `source_path` in it exists on disk; sections 5 and 6 now also accept unquoted `assets:` entries, fail on an `exclude:` key (not evaluated) and use exact tripwire counts.
- `source-manifest-builder`: a scope note says it is not for the ai-assets repo itself (one publisher from `skaile.manifest.yaml`, the glob walk is load-bearing; an `assets:` inventory or `publisher_overrides` fail `skaile-manifest.test.sh` / `source-publishers.test.sh`).
- `DOMAIN.md`: the `tools/` row (no such folder; the scaffold scripts sit under `skills/skill-builder/scripts/` and `skills/domain-builder/scripts/`) is replaced by an `agents/` row for `skaile`, and `agents:` in the frontmatter names it. `external/DOMAIN.md` says to track provenance in a `sources.md` next to it (the `docs:` key is gone).
- `ai-asset-management` preset: consumers need a second `sources:` entry for `https://github.com/skaile-ai/ai-assets-skaileup` next to `skaile-ai/ai-assets`. The preset ships `agent:@skaile-ai/skaile`, which composes three delegate agents (`skaileup-conceptualize`, `impl-build-implement`, `quality`) that ship from that repo under the same publisher; without it the preset does not resolve completely. (The `skaile-development` preset no longer needs it, see its CHANGELOG.) The preset file carries the same note.
- `catalogs/`: `build-pipeline.catalog.yaml` and its compiled `dist/build-pipeline.catalog.json` are removed: every one of its 39 `assets:` entries and all six `include:` globs named three domains (`skaileup-conceptualization`, `skaileup-implementation`, `skaileup-evaluate`) that exist in no repo any more (`ai-assets-skaileup` is numbered `01_concept` … `13_impl-quality`, with different skill names). `scripts/presets-resolve.test.sh` now checks every `assets:` entry and `include:` glob of the five remaining `*.catalog.yaml` files against the tree; a cross-repo entry would go on its `EXTERNAL_REFS` allowlist as `catalog:<entry>`.
- `agent-builder`: the `extends` examples use a generic `../parent-agent/agent.yaml` (no shipped agent inherits any more) and say to prefer composing the needed parts directly, since only `skaile install` follows `extends`.
- Repo-level publishing: `.skaile-source.yaml` (the v1 file) now agrees with `skaile.manifest.yaml`, the canonical publish manifest. The per-folder `publisher_overrides` are gone (`catalogs/` → `@skaile` was the one non-default override: every other entry only restated the folder-name default, for example `use/` → `@use`; no consumer references `@skaile/` catalog refs: a grep of forge, platform and store finds only a mock dependency list in a Forge Storybook story and a store proposal doc) and `publisher_default` is `@skaile-ai`: the store's sync reads `skaile.manifest.yaml` first, so every asset already published as `@skaile-ai/<name>`, and the overrides only mislead v1 readers such as the curation preview. `scripts/source-publishers.test.sh` asserts the agreement instead of per-folder publishers. `DOMAIN.md` drops the `docs:` key and `docs/` row (there is no `docs/` folder).
- `agent-builder`: the `extends` guidance says what the merge does (every object-valued key replaced wholesale, `composes` parent + child, other arrays such as `tags` unioned; install reads the manifest only, the parent's `SOUL.md`/`RULES.md` are not inherited, an item that arrives only through `extends` is not rendered) instead of "override any field locally", and the `delegation.mode` bullets (`explicit`, `router`, `auto`) match `docs/agents.md`: `explicit` means sub-agents are called from skill prompts, not "acts alone", and the `knowledge/index.yaml` example uses the `documents:` shape the runtime and the shipped files use.
- Agent `skaile`'s `SOUL.md` and the shared persona `skaile-base` (`_agent-parts/personas/skaile-base/PERSONA.md`) are rewritten from first to second person ("You are Skaile …"), the voice of every other `SOUL.md`; a composed persona is appended after `SOUL.md`, so both must address the model the same way. `agent-builder` and `docs/agents.md` say so, and `docs/agents.md` no longer says knowledge is "loaded" in priority order (it is discoverable, not inlined).
- `agent-builder`: the `extends:` example in `references/gitagent-spec.md` is a relative path inside the repo (a git URL is an upstream-GitAgent feature, not accepted here), and the knowledge token-budget advice no longer assumes inlining.
- `agent-builder`: teaches `spec_version: "0.2"` instead of 0.1: `composes:` items (kinds, slot ids, bindings, delegates), `lifecycle`/`io` for role agents, `memory.blocks`, `triggers`, and `extends:` semantics. The worked example is the real `knowledge-research/agents/researcher`. `references/gitagent-spec.md` follows. The skill has no `version:` of its own (skill versions come from the repo tag), so there is nothing to bump.
- Agent `skaile` 1.1.0 moves to `spec_version: "0.2"`: `persona:` / `rules:` / `requires:` become `composes:` items. The persona and ruleset parts are now `_agent-parts/personas/skaile-base/PERSONA.md` and `_agent-parts/rules/skaile-safety/RULESET.md` (1.1.0). The delegate agents are catalog refs (`skaileup-conceptualize`, `impl-build-implement`, `quality`); the `architecture` delegate is dropped everywhere (`composes:`, its `agents.architecture` block with the three `*_requested` triggers, the `architecture` tag, and the "four domain agents" wording in the description and `SOUL.md`) because no such agent is published; the `skaile` agent's `SOUL.md` now says it handles architecture questions itself. The shared `PERSONA.md` no longer counts delegates ("orchestrating specialized domain agents"): the roster belongs to each agent's `composes:` list and `SOUL.md`, not to a part other agents reuse.
- `ai-asset-management.bundle.yaml` → `ai-asset-management.preset.yaml` (preset `@skaile-ai/ai-asset-management` 1.0.0).
- Agent `skaile`: `metadata.routing_notes` is renamed `metadata.dropped_delegates` (it records why the `architecture` delegate was dropped); `routing_notes` now means "where to route" only, as in `skaile-development`.
- `source-manifest-builder`: the scaffold stub uses a literal publisher plus `publisher_overrides`, since @skaile/workspaces 5.0 rejects the `"@<domain>"` template.
- `source-manifest-builder`, `source-sidecar-curator`: the publisher review question asks about the resolved publisher instead of a folder-derived one, which 5.0 no longer produces.
